## Findings

### Verdict
- Prior art supports half of the current design. An explicit, agent-issued "done" action is the one completion signal seen in a primary source (Gas Town: the polecat runs `gt done`, which pushes the branch and creates a merge-request bead). A report file is our variant of that idea, not something I found any project doing. Other projects detect completion from hooks or session files instead (maniple: stop-hook markers and session JSONL files; Claude Code `Stop`; Codex `turn/completed`). A wrapper that translates each CLI's activity into `pane report-agent` states is not supported as a data-only contract: every project that reports live state does it with code per harness (hooks, plugins, extensions, or a native RPC adapter).
- Better default for a data-only generic driver: completion = report file + process exit (works on any CLI, state-free). Treat live state as best-effort and never gate on it. Where steering mid-run matters, ACP over stdio is the only protocol found that gives all three channels from a command line alone.
- A2A does not fit (agent-to-agent over HTTP between servers; no CLI adapters found). MCP-as-callback works only if the CLI loads an MCP config, which is per-CLI config again.

### Pattern 1: terminal screen scraping + send-keys
- claude-squad: `tmux capture-pane -p -e -J`, SHA-256 of the pane text for "changed", substring match for a prompt per program: Claude "No, and tell Claude what to do differently", Aider "(Y)es/(N)o/(D)on't ask again", Gemini "Yes, allow once". Keys are written raw to the tmux PTY, Enter = 0x0D. Trust prompts auto-dismissed by string. cited https://raw.githubusercontent.com/smtg-ai/claude-squad/main/session/tmux/tmux.go ; README lists `-y/--autoyes` as experimental for Claude Code and Aider and names Claude, Codex, Gemini, Aider, OpenCode, Amp, AGPL-3.0, cited https://github.com/smtg-ai/claude-squad .
- Other tmux scrapers use the same trick ("Do you want to" marker over the bottom region; shell loops greping "Do you want to proceed?" and sending Enter): cited-snippet https://docs.rs/crate/bosun-tmux/0.3.6/source/src/tmux/detector/claude.rs . Not read as primary pages.
- herdr itself is this pattern as a product: screen manifests give `idle|working|blocked|done|unknown`, "blocked = approval or question UI recognized", manifests update remotely; hook reports override screen where an integration owns lifecycle. cited-snippet via raw/2026-11-13-quaqua-rs-herdrkind.md (`herdr --skill`, CHANGELOG lines) and https://herdr.dev/docs/add-herdr-support/ .
- Blocked-on-permission: yes, by matching the dialog text. CLI needs: a TUI with stable dialog text. Fails: any wording change in a CLI release breaks detection (claude-squad hardcodes three strings); program matched by name only (`==` vs `HasSuffix` mismatch inside the same file, same tmux.go); "idle" is inferred from the screen not changing, so a long thinking pause looks idle; send-keys into the wrong mode types into the wrong UI (inferred).

### Pattern 2: agent-side hooks / notify callbacks
- Claude Code: `Notification` hook with matcher `permission_prompt|idle_prompt` (also `agent_needs_input`, `agent_completed`), `Stop`, `StopFailure`, `PermissionRequest`, `SessionStart/End`; hook gets JSON on stdin with `session_id`, `transcript_path`, `cwd`, `hook_event_name`; `Stop` carries `last_assistant_message`; a hook can allow/deny via `decision.behavior`; `onFailure: block` exists. cited https://code.claude.com/docs/en/hooks (first 100k of 294k chars read).
- Codex `notify = ["cmd", ...]`: runs the command with one JSON argument, fires "currently only `agent-turn-complete`", fields `type, thread-id, turn-id, cwd, input-messages, last-assistant-message`. Approval is only a terminal bell via `tui.notifications = [..., approval-requested]` (OSC9/BEL), not a callback. cited https://learn.chatgpt.com/docs/config-file/config-advanced .
- opencode plugins load from `.opencode/plugins/` or `~/.config/opencode/plugins/` (TS/JS). The event list is on a page I could not read (`/build/plugins`). cited https://opencode.ai/docs/plugins/ for loading only.
- pi extensions (TS): events `agent_start`, `agent_end`, `agent_settled`, `turn_end`, `tool_call` (can return `{block:true}`), `ui_prompt_start/end`; `ctx.ui.confirm` needs a UI (print/JSON mode has none). cited https://raw.githubusercontent.com/badlogic/pi-mono/main/packages/coding-agent/docs/extensions.md (first 100k of 158k chars).
- opencode (follow-up read): the plugin server docs list hooks, not events: `ctx.permission.hook("evaluate")`, `ctx.tool.hook("execute.before"/"execute.after")`, `ctx.session.hook("prompt"|"retry"|...)`, `ctx.shell.hook("create.before")`; events are subscribed with `ctx.event.subscribe({types})` and the page names only `config.updated`, `worktree.updated`, `server.connected`. I could not confirm `session.idle` or `permission.asked`, so opencode's blocked/idle callback is unverified. cited https://opencode.ai/docs/build/plugins/server .
- Users: Gas Town (Claude Code hooks in `.claude/settings.json` for mail inject; Copilot lifecycle hooks; runtimes without hooks such as Codex use a startup `gt nudge` fallback) cited https://github.com/gastownhall/gastown ; piggery (sessions via Claude plugin+MCP, Codex hooks+MCP, pi/omp extension, opencode plugin) cited https://github.com/sting8k/piggery ; maniple reads stop-hook markers (cited https://github.com/Martian-Engineering/claude-team).
- CLI needs: a hook system. Claude: JSON config, data-only. Codex: one TOML key, data-only (but turn-complete only). opencode and pi: code files. Fails: coverage differs per CLI (Codex has no blocked event); hooks load from project/user config so a project can shadow them, and `claude --bare` skips hooks entirely (cited https://code.claude.com/docs/en/headless); hook failure default is non-blocking.

### Pattern 3: headless / RPC / server modes
- `claude -p`: `--output-format json|stream-json`, final `result` message with cost (`total_cost_usd`), `session_id`; `--resume <id>`/`--continue` for a follow-up; exit 0 on success, non-zero on failure, 143 on SIGTERM; unlisted tool needing approval is denied in manual `-p` mode unless a `PermissionRequest` hook or `--permission-prompt-tool` answers; `--permission-prompts none` denies without waiting; `permission_denied` system messages in the stream. cited https://code.claude.com/docs/en/headless . Caveat: `-p` can stay open for background work, 10 min cap.
- `codex exec`: `--json` JSONL events `thread.started, turn.started, turn.completed, turn.failed, item.*, error`; `-o/--output-last-message <file>`; `--output-schema`; `codex exec resume <id>`; read-only sandbox by default; no interactive approval; exit codes not documented. cited https://learn.chatgpt.com/docs/non-interactive-mode .
- `codex app-server`: JSON-RPC over stdio JSONL, `initialize` then `thread/start`, `turn/start`, `turn/steer`, `turn/interrupt`, notifications `turn/started`, `turn/completed` (status `interrupted` after cancel); server-initiated approval requests (`item/permissions/requestApproval`, `mcpServer/elicitation/request`); experimental API gated by `capabilities.experimentalApi`; WebSocket transport "experimental and unsupported". cited https://learn.chatgpt.com/docs/app-server (first 100k of 148k chars).
- `opencode serve`: HTTP on 127.0.0.1:4096, optional basic auth, `POST /session/:id/message` (waits) and `/prompt_async` (204), `GET /event` SSE, `GET /session/status`, permission reply `POST /session/:id/permissions/:permissionID {response, remember?}`; permission event payload not documented on that page. cited https://opencode.ai/docs/server/ .
- `pi --mode rpc`: JSONL on stdin/stdout, commands `prompt, steer, follow_up, abort, get_state, ...`; `agent_end` ends one low-level run only, wait for `agent_settled`; extension UI via `extension_ui_request`/`extension_ui_response`; closing stdin = orderly shutdown. cited https://raw.githubusercontent.com/badlogic/pi-mono/main/packages/coding-agent/docs/rpc.md .
- Users: piggery workers run `claude -p`, `codex app-server`, `opencode serve`, `pi --mode rpc`, `omp --mode rpc`, `dsh --profile sdk` (cited piggery README); T3 Code runs adapters per provider, subprocess/RPC (cited in raw/2026-11-13-quaqua-rs-priorart.md).
- CLI needs: a headless mode. Fails: each protocol differs, so a generic driver needs one parser per protocol (code per harness); one-shot modes have no "blocked" state (a denied call just fails or is skipped); resume semantics differ; app-server/RPC fields are marked experimental or unsupported in places.

### Pattern 4: Agent Client Protocol (ACP, Zed)
- JSON-RPC 2.0, agents "typically run as subprocesses", stdio. `session/prompt` starts a turn and its response carries a `stopReason` (`end_turn, max_tokens, max_turn_requests, refusal, cancelled`); `session/update` notifications stream message chunks, tool calls (`pending, in_progress, completed, failed`), plans, mode changes; the agent asks `session/request_permission` with `options` of kind `allow_once|allow_always|reject_once|reject_always` and the client answers `selected` or `cancelled`; `session/cancel` interrupts. cited https://agentclientprotocol.com/protocol/overview , /protocol/prompt-turn , /protocol/tool-calls .
- Coverage today (cited https://agentclientprotocol.com/overview/agents): Claude via Zed's `claude-agent-acp` (wraps the Claude Agent SDK; has a `preview` npm channel built on every push to main), Codex via `agentclientprotocol/codex-acp` (wraps the Codex App Server, 646 commits, 81 open issues; "preview builds skip CI"), Pi via third-party `svkozak/pi-acp`, Gemini CLI and OpenCode listed without a separate adapter. Native commands: `gemini --acp` (stdio, `initialize, authenticate, newSession, loadSession, prompt, cancel, setSessionMode`; cited https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/acp-mode.md) and `opencode acp` (cited https://opencode.ai/docs/acp/ ; `/undo` and `/redo` unsupported).
- So ACP exists today for all five (claude, codex, opencode, pi, gemini), but three of them (claude, codex, pi) go through a separate adapter package with its own release cadence; only `pi-acp` is third party (claude-agent-acp is Zed's, codex-acp is under the ACP org). codex-acp latest release v2.6.0, 2026-11-06 (cited https://github.com/agentclientprotocol/codex-acp/releases).
- A driver that already does this: the OpenHands SDK `ACPAgent` takes `acp_command` + `acp_args` (+ secrets), speaks JSON-RPC over stdio, auto-grants every permission request ("make sure you trust the ACP server"), and records cost from `PromptResponse.usage` (per turn tokens) and `UsageUpdate` notifications (cumulative cost, context size). Examples use `@agentclientprotocol/claude-agent-acp`. cited https://docs.openhands.dev/sdk/guides/agent-acp.md . This is the closest prior art for "configure an unknown agent from command + args only".
- Gives all three channels: state from `session/update` + pending `request_permission` (= blocked) + open `session/prompt` (= working); prompt in = `session/prompt`; completion = the `session/prompt` response with stopReason. Cost: OpenHands reads token usage and cumulative cost from `PromptResponse.usage` / `UsageUpdate` (cited above), so ACP can carry cost where the adapter fills it; whether each adapter does was not checked. Not seen: any rule that keeps a worker's permission mode fixed (`setSessionMode` exists in Gemini's list).
- Fails: needs a JSON-RPC client in the driver (written once, not per harness); loses the visible TUI pane (a herdr pane would show only the adapter's stderr, inferred); adapter bugs show up as harness bugs; stopReason `end_turn` is the model finishing, not "the task is done" so the report file is still needed (inferred).

### Pattern 5: A2A
- Task states `SUBMITTED, WORKING, INPUT_REQUIRED, AUTH_REQUIRED` (interrupted) and `COMPLETED, FAILED, CANCELED, REJECTED` (terminal); `SendMessage` blocks until terminal/interrupted unless `returnImmediately`; streaming and webhook push notifications; JSON-RPC, gRPC or HTTP+JSON bindings; agent card for discovery. cited https://a2a-protocol.org/latest/specification/ (first 100k of 257k chars).
- Inferred: it maps cleanly onto our three channels (INPUT_REQUIRED = blocked, COMPLETED + artifact = result) but I found no coding CLI that speaks it; it needs an HTTP server per agent, so a CLI would need a wrapper process. Not a fit for launching unknown CLIs. I did not search for A2A adapters of coding CLIs beyond this, so "none exist" is unverified.

### Does prior art support the current design?
Current: unknown CLI in a herdr pane, args template, wrapper reports state via `pane report-agent`, report file = completion.
- Report file as completion: not found in any primary source as such. The nearest is an explicit agent-issued done action (Gas Town `gt done`); other tools use hooks or session files (maniple). A report file is still sound for a generic driver because it needs no CLI feature; keep it written atomically, plus process exit as the failure signal. Say in the plan that this is our own contract, not a borrowed one.
- Wrapper reporting state: the cheap wrapper can only know what a process can know without CLI help: started, running, exited. That gives `working` and `idle`/gone, never `blocked`, so "blocked" must come from herdr's screen manifest (only for the 24 kinds) or from a hook or ACP. A wrapper that reads the CLI's output to guess state is Pattern 1 again, with code per harness.
- Therefore the degraded-mode wording in R6 (cost `unknown`, unverified stop, cannot review) is consistent with prior art; adding "blocked unknown" to that list would be honest. Q37 stays open: whether `agent wait/prompt` accept a reported-only agent is not answered by any docs fetched (herdr docs say reporting enables `agent wait`, and are silent on `agent prompt`; cited https://herdr.dev/docs/add-herdr-support/).

### Ranked shortlist (contracts that fit a generic driver configured from data only)
1. Headless exec + report file + exit code. Config: `command`, `args` template (`{model} {prompt} {cwd}`), optional `resume_args`, `output_flag`. Works for `claude -p`, `codex exec`, and any CLI with a one-shot mode. Completion = report file present AND exit seen; failure = exit without file. Trade-offs: no mid-run steering (use resume for follow-ups), no blocked state (permissions must be pre-set, which R11 already wants), cost only if the CLI prints it (Claude `total_cost_usd` yes; Codex tokens only, per raw codex-flags note), no live view unless the process runs in a pane. Best default for workers because it has the fewest CLI requirements.
2. ACP over stdio. Config: `command`, `args` (e.g. `gemini --acp`, `opencode acp`, `codex-acp`, `claude-agent-acp`, `pi-acp`), permission policy as data (`allow_once` etc. mapped to options). Gives state, prompt, stopReason and permission handling from one client the driver implements once. Trade-offs: separate adapter packages for three of five CLIs (claude-agent-acp also ships a preview channel), cost depends on the adapter filling `UsageUpdate` (OpenHands reads it, so it exists in the protocol), no TUI, completion still needs the report file for "task done". Best for steerable or review roles and for the "blocked" channel. Strongest prior art for the data-only claim: OpenHands `ACPAgent` is configured by `acp_command` + `acp_args`.
3. Pane + screen manifest + hook where data-only (Claude `Notification`/`Stop` via JSON settings, Codex `notify` via one TOML key), report file for completion. This is the current design with the wrapper removed. Trade-offs: state quality differs per CLI, hooks can be shadowed, blocked detection exists only where herdr or Claude hooks provide it. Keep as the visibility option, not the contract.

Not recommended as a default: MCP callback (relies on model compliance and per-CLI config), A2A (no CLI support found), per-harness native RPC (code per harness, which R6 rules out).
