## Correctness check
`CARGO_TARGET_DIR=target/sc2 ... cargo test -p qq-core status` from the sccache build: `running 4 tests ... test result: ok. 4 passed; 0 failed` (all other binaries 0 matched, ok).

## Decision: NO change to spawn env — evidence only
- A cold qq-core test build is **15–42 s at 4 jobs**, not minutes. The 41 s first run was inflated by incremental compilation and a cold page cache; with CARGO_INCREMENTAL=0 the same cold build takes 15.5 s with no sccache at all.
- sccache gave no win: cold 16.6 s (vs 15.5 s control), "warm" 31–40 s (slower, 0 % Rust hits), plus a 3m50s one-time install, a daemon, and cache dirs to manage.
- A shared CARGO_TARGET_DIR would save at most ~15–40 s per worker while risking the stale-test-binary-across-trees failure seen earlier, and lock contention between parallel builds.
- The machine freeze is a concurrency problem (many parallel builds), not a per-build duration problem; the existing load/job limits (CARGO_BUILD_JOBS=4, nice) are the lever. If anything is worth trying, it is CARGO_INCREMENTAL=0 for workers' one-shot builds (≈2.7× faster cold here, n=1 each, load differed) — not applied; needs a repeat measurement and the incremental rebuild trade-off for edit-test loops.
- Caveats: single run each, other workers' load varied (load1 3.8–11); page cache state differed between the first run and the rest.
