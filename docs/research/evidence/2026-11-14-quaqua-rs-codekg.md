## Verdict
The evidence does NOT support a stored code graph as the default at this scale (about ten repos, one machine, three languages). Workers get symbol/reference answers from LSP-on-demand with zero refresh job and zero write path. A stored graph adds a refresh job, staleness and a write path for answers that grep plus LSP already give. It earns its place only for transitive call-graph questions ("who calls X, 3 hops") that LSP does not answer in one call. R10's premise ("a stored graph built by someone other than workers") is workable but is an optimisation, not a need; Q39 should start from "no stored graph" and add one only if workers demonstrably ask call-graph questions.

## Shortlist (ranked, fits R10)
1. No stored graph: LSP on demand through Serena (all three languages, one MCP server, v2.1.0).
   - Refresh trigger: none. Language servers read the working tree.
   - Read-only: the PROJECT config has `read_only: false` with the comment "If set to true, all editing tools will be disabled and attempts to use them will result in an error" (cited project.template.yml); `excluded_tools` also exists. The global template has no such flag (only `read_only_memory_patterns`). So the write path to source can be closed by configuration alone; memories (`write_memory`, `edit_memory`, `delete_memory`) are separate tools, so exclude them too (inferred that read_only may not cover them). Serena still writes `.serena/` caches and memories inside the project root (cited), so give workers a read-only checkout or point `project_serena_folder_location` at a non-repo directory. Read tools: find_symbol, find_referencing_symbols, find_declaration, find_implementations, get_symbols_overview, search_for_pattern, read_file (cited tools page).
   - Trade-offs: GPL-3.0 app (fine to run as a separate process, inferred); LSP cold start per session; no call-hierarchy tool in Serena's list (cited), so "who calls X, 3 hops" is repeated find_referencing_symbols calls; LSP's own call hierarchy has prepare/incomingCalls/outgoingCalls requests (LSP 3.17 spec lists the three methods in its table of contents; per-level behaviour NOT confirmed from the spec text, inferred); needs the three language servers installed.
   - Cheaper variant for Go: `gopls mcp` (>= v0.20), but it can run `go` and download modules (cited).
2. codebase-memory-mcp, built and refreshed by a CoS/Supervisor job (the "stored graph" choice).
   - Refresh trigger options: (a) on merge into the integration branch (CoS runs `index_repository` after the gate); (b) built-in background watcher (cited), which means a long-lived writer process, so run it as the CoS's, not a worker's; (c) scheduled Supervisor job. Prefer (a): deterministic and journaled.
   - Read-only: no read-only mode documented (cited: `index_repository` and `manage_adr` write). Enforce outside the tool: workers get a read-only mount of the cache dir (inferred) or a CoS-run wrapper that exposes only the query tools. This is a real gap for `kb_worker_read_only`.
   - Trade-offs: one binary, MIT, call graph included; refresh time unknown for our repos (self-reported Django full index about 6 s on an M3 Pro, cited, not ours); extra daemon; staleness between merges.
3. SCIP per repo (rust-analyzer scip, scip-typescript, scip-go), written by a CoS job on merge.
   - Most precise (compiler-level references), all Apache-2.0, files are plain artifacts that can be committed or journaled.
   - But there is no query or serve command (cited), so we must write the reader (`scip print --json` or `expt-convert` SQLite, which is experimental). Three tools, three setups; scip-go README says indexing without the `go` binary is incomplete. Highest build cost, lowest runtime risk.

Rejected: stack-graphs (archived), ctags (definitions only), aider repo map (not standalone), CodeGraphContext (needs a graph DB and Python; a heavier cousin of #2).
